2. luxury_prototype.py — build_prototype
Verdict: PARTIAL.
It genuinely writes Python component and test files, runs unittest in a subprocess, records return codes and reported test counts, and returns a receipt. But it proves only that the supplied tests ran and passed—not that the components implement the intended mechanisms correctly, integrate with real systems, or satisfy the venture's requirements.
Specific code-level findings:
Template selection: if lever not in COMPONENTS or not _SAFE.match(lever) rejects unsupported lever names and names outside the permitted character pattern. This is a real guard, but it does not validate the contents of COMPONENTS.
File generation: write_text(textwrap.dedent(code).lstrip()) writes the selected template to disk. This is real file generation, not proof of a functional application.
Test execution: subprocess.run([... "-m", "unittest", f"test_{lever}", "-v"], ...) executes tests, but there is no explicit clean environment, dependency isolation, or protection against stale files.
Test accounting: re.search(r"Ran (\d+) tests?", p.stderr) extracts the test count from stderr. If the expected summary is absent, the function records zero; it does not distinguish all causes of missing test summaries.
Pass determination: all(r["returncode"] == 0 and r["tests_run"] > 0 for r in results) establishes that every recorded run exited successfully and reported at least one test. It cannot detect weak assertions, mocked-away functionality, or tests that merely confirm hard-coded outputs.
Output receipt: The returned all_tests_passed is a meaningful report of the implemented test gate, but not a general certification of prototype correctness.
3. Top five concrete weaknesses
1
The scoring system manufactures apparent precision.
_score() uses fixed weights, caller-assigned importance and readiness, token overlap, and a risk formula based on constraint count. The resulting weighted_total can rank concepts deterministically without demonstrating that the ranking predicts real customer demand or implementation success. _DIFF also assigns fixed differentiation scores based on a supplied label, not a documented prior-art search.
2
The pitch package can misrepresent the selected concept's validation plan.
build_pitch_package() selects c using the requested concept_id, but obtains experiment from studio['validation_experiment'], which belongs to the studio's recommended winner. If the caller requests another concept, the package combines that concept with the winner's experiment and success metric.
3
The outreach validator is easy to bypass semantically.
validate_outreach_preview() checks five literal substrings: partnered with, official partner, guaranteed, validated demand, and endorsed by. It does not check equivalent claims, misleading implications, other unsupported factual statements, or whether the proposed recipient and evidence are legitimate. Passing this check is not proof that a message is safe or truthful.
4
The prototype test gate is vulnerable to stale artifacts and weak tests.
build_prototype() writes into an existing directory without cleaning it, then invokes tests by module name. Old files can remain and contaminate later discovery or results. A zero exit code and a positive test count do not establish meaningful behavioral coverage; the unseen templates and tests are essential to assessing actual functionality.
5
Outcome reporting and evidence handling stop at structural checks.
summarize_outcome() trusts the submitted measurements and source references. Source checks only URL syntax and string lengths, while build_luxury_venture() checks referential integrity rather than whether the cited findings substantiate the signals. The system can therefore produce internally consistent packages built on inaccurate or irrelevant evidence.
