Everything below the pin is DESIGN text (spec-author rulings and builder choices), not her words.

## What it does
`run(request) -> dict`. From a supplied template, profile and opportunity list it classifies each fee as free,
unknown or positive and returns DRAFTS (recipient, subject, body, content-hash id) for positive fees only.
Stdlib only, offline, deterministic (no clock; `as_of` is echoed into `scope` only). Entry file
`backend/app/modules/c35/waiver_drafts.py`; `c35/__init__.py` is untouched (empty). No HTTP handler, no catalog
registration (integrator's job).

## What it does not do (LIMITS)
- No sending, registering, submitting, fee action, payment, login or credential use. The module has one public
  function (`run`) and imports no network, process, file, clock or random module (tests assert this).
- No approval recording. Status is always `awaiting_exact_draft_approval`; any future external action needs her
  explicit yes, which no input field can supply. Competitions are parked (her 10-09 order, peer-stated): prep only.
- Does not claim a waiver will be granted. No scraping, no live lookups.
- Forbidden-key matching is exact after casefold and "-" to "_" (bounded list). `access-token` is caught;
  `x_token`, `tokens`, `sender_name` pass. Values are never scanned. This is a stated limitation, not a security proof.
- Recipient format check is a loose regex plus a no-control-character check; it does not verify the mailbox exists.

## Input (closed schema: unknown keys refuse the whole request)
`{"as_of":"YYYY-MM-DD","profile":{"name","school"},"opportunities":[{"id","title","fee","contact_email",
"contact_name"?,"deadline"?}],"template":"...","strict"?:bool}`
Allowlists: top level {as_of, profile, template, opportunities, strict}; profile {name, school};
opportunity {id, title, fee, contact_email, contact_name, deadline}. `opportunities` must be a list.

## Check order (peer text 17:23, first failure raises; an earlier step beats a later one; first item wins)
1 request is a dict. 2 forbidden-key scan (recursive over dict keys, through dict values and list/tuple items).
3 non-str dict key anywhere -> BAD_TYPE:key, only if step 2 found nothing. 4 unknown-key allowlists: top level,
then profile, then each opportunity in list order. 5 top-level types: as_of (str), profile (dict), template (str),
opportunities (list; empty -> EMPTY), strict (bool if present). 6 top-level caps in this order: opportunities
length, template, as_of, profile values (sorted key order). ISO date shape of as_of (after the caps, before clean_text; peer 2b85fb24). 7 clean_text on as_of, profile
name/school, template. 8 per opportunity in list order: element/field types, then caps, then clean_text on its
text fields; after the whole pass duplicate ids. 9 fee classification in list order. 10 placeholders. 11 strict
recipient check.

## Fee grammar (peer-stated)
After strip and casefold: FREE = free, 0, 0.0, 0.00, usd 0, $0, no fee, none, numeric 0, or any parsed amount of 0.
UNKNOWN (listed in `fee_unknown`, no draft) = "", n/a, tbd, unknown, varies, None or missing. Positive =
`^(cur\s?)?(\d{1,3}(,\d{3})+|\d+)(\.\d{1,2})?(\s?cur)?$` with cur in usd/eur/gbp/inr (+ rs, $, euro, pound,
rupee symbols as prefix only), `re.ASCII`. Anything else, bool, negative, nan/inf: BAD_TYPE:fee for the WHOLE
request. A prefix plus a suffix currency together is BAD_TYPE:fee; a positive int/float is drafted with `{fee}` =
str(value) (both peer-confirmed 17:18).

## Template
Allowed placeholders: {name} {school} {opportunity} {contact} {fee} {deadline}. `{contact}` = contact_name else
"Admissions Team". `{fee}` = raw stripped fee string. `{deadline}` = opportunity.deadline. A missing/blank value
is UNFILLED:<name|school|deadline> only if the template uses that placeholder. Any other `{x}` (including `{}`) is
UNFILLED:template (the placeholder text is untrusted and is not echoed), checked even if no opportunity is
drafted. Substitution is single-pass: values containing braces are not re-expanded. Template and body keep
LF/CR/TAB byte-exact.

## Draft
`draft_id` = sha256(json.dumps([recipient or "", subject, body], ensure_ascii=False, separators=(",",":"))
.encode("utf-8")).hexdigest()[:16]. Subject = `Fee waiver request: <title>`. Missing/blank recipient: recipient
null, `needs_recipient` true. Invalid format (`^[^@\s]+@[^@\s]+\.[^@\s]+$` or any control char): recipient null
(the invalid string is not carried), `needs_recipient` true, `recipient_invalid` true; never raises except under
`strict`. `strict:true` raises `APPLY_REFUSED_NORECIPIENT:contact_email` for the first drafted opportunity in list
order that needs a recipient (free/unknown ones are ignored). Output:
`{drafts (input order), skipped_no_fee (sorted ids), fee_unknown (sorted ids), scope}`. Ids are kept byte-exact.

## Forbidden keys (casefold, "-" to "_", exact; whole request refused)
Precedence SEND > SPEND > SUBMIT > NOCREDS; within the winning class the alphabetically first MATCHED table key is
the suffix (`APPLY_REFUSED_SEND:approval_token`); non-matching key text is never echoed.
- SEND: send, approve, approved, approval, approval_token, smtp, token, email_send, sender, smtp_host, smtp_port, smtp_user
- SPEND: pay, waive_fee, fee_action
- SUBMIT: register, submit, attempt
- NOCREDS: login, password, username, credentials, otp, api_key, access_token, refresh_token, bearer, pass, passwd
The table is peer-stated identical to S4.8's (17:18). The earlier S4.8 SEND-list difference was reported by the
peer's summary only; it is not resolved here beyond the peer's statement.

## Choices the filed text left open (settled by the peer in 2b85fb24, 17:41; peer-stated, not owner words)
1. `EMPTY` for an empty opportunities list has no suffix (literal reading); an `EMPTY:opportunities` form is the alternative.
2. `opportunities` must be a `list` (a tuple is BAD_TYPE:opportunities); the forbidden/non-str scan still walks tuples.
3. (peer-settled 2b85fb24) Step 5 checks only that `as_of` is a str; the caps run next, then the ISO shape (BAD_TYPE:as_of, so "" and control characters are BAD_TYPE:as_of), then clean_text. An over-long as_of is OVERSIZE:as_of.
4. A blank (whitespace or empty) profile name/school counts as MISSING (UNFILLED only if used), not EMPTY; None is also missing.
5. Within step 8 an opportunity's field types are checked as id, title, contact_name, deadline, then contact_email (the recipient shape), then caps id, title, contact_name, deadline, then clean_text in the same order.
6. contact_name and deadline may be blank strings (blank contact_name falls back to the default; blank deadline is missing).
7. An invalid recipient string is not carried (recipient null); strict treats missing and invalid the same.
8. Top-level unknown-key suffix is `request` (no schema parent field exists above the request).
9. policy.check is not called (its six rules have no code path here); policy.clean_text and policy.scope are used.
