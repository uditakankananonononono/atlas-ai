# S4.3 fee-waiver-draft-queue (c35.waiver_drafts) - PREP ONLY

Supplied requirement excerpt: "if there is fee, emails for fee waivers"
The design below narrows this requirement to offline drafts. Source-message identity
is not independently established by matching excerpt text. Design choices below
are implementation interpretations, not a quotation of the requirement.

## What it does
`run(request) -> dict`. From a supplied template, profile and opportunity list it classifies each fee as free,
unknown or positive and returns DRAFTS (recipient, subject, body, content-hash id) for positive fees only.
Stdlib only, offline, deterministic (no clock; `as_of` is echoed into `scope` only). Entry file
`backend/app/modules/c35/waiver_drafts.py`; `c35/__init__.py` is untouched (empty). No HTTP handler, no catalog
registration.

## What it does not do (LIMITS)
- No sending, registering, submitting, fee action, payment, login or credential use. The module has one public
  function (`run`) and imports no network, process, file, clock or random module (tests assert this).
- No approval recording. Status is always `awaiting_exact_draft_approval`; any future external action needs an
  explicit approval from the person the drafts are for, which no input field can supply. This unit is prep only.
- Does not claim a waiver will be granted. No scraping, no live lookups.
- Forbidden-key matching is exact after casefold and "-" to "_" (bounded list). `access-token` is caught;
  `x_token`, `tokens`, `sender_name` pass. Values are never scanned. This is a stated limitation, not a security proof.
- Recipient format check is a loose regex plus a no-control-character check; it does not verify the mailbox exists.

## Input (closed schema: unknown keys refuse the whole request)
`{"as_of":"YYYY-MM-DD","profile":{"name","school"},"opportunities":[{"id","title","fee","contact_email",
"contact_name"?,"deadline"?}],"template":"...","strict"?:bool}`
Allowlists: top level {as_of, profile, template, opportunities, strict}; profile {name, school};
opportunity {id, title, fee, contact_email, contact_name, deadline}. `opportunities` must be a list.

## Check order (first failure raises; an earlier step beats a later one; first item wins)
1 request is a dict. 2 forbidden-key scan (recursive over dict keys, through dict values and list/tuple items).
3 non-str dict key anywhere -> BAD_TYPE:key, only if step 2 found nothing. 4 unknown-key allowlists: top level,
then profile, then each opportunity in list order. 5 top-level types: as_of (str), profile (dict), template (str),
opportunities (list; empty -> EMPTY), strict (bool if present). 6 top-level caps in this order: opportunities
length, template, as_of, profile values (sorted key order). ISO date shape of as_of (after the caps, before clean_text). 7 clean_text on as_of, profile
name/school, template. 8 per opportunity in list order: element/field types, then caps, then clean_text on its
text fields; after the whole pass duplicate ids. 9 fee classification in list order. 10 placeholders. 11 strict
recipient check.

## Fee grammar
After strip and casefold: FREE = free, 0, 0.0, 0.00, usd 0, $0, no fee, none, numeric 0, or any parsed amount of 0.
UNKNOWN (listed in `fee_unknown`, no draft) = "", n/a, tbd, unknown, varies, None or missing. Positive =
`^(cur\s?)?(\d{1,3}(,\d{3})+|\d+)(\.\d{1,2})?(\s?cur)?$` with cur in usd/eur/gbp/inr (+ rs, $, euro, pound,
rupee symbols as prefix only), `re.ASCII`. Anything else, bool, negative, nan/inf: BAD_TYPE:fee for the WHOLE
request. A prefix plus a suffix currency together is BAD_TYPE:fee; a positive int/float is drafted with `{fee}` =
str(value).

## Template
Allowed placeholders: {name} {school} {opportunity} {contact} {fee} {deadline}. `{contact}` = contact_name else
"Admissions Team". `{fee}` = raw stripped fee string. `{deadline}` = opportunity.deadline. A missing/blank value
is UNFILLED:<name|school|deadline> only if the template uses that placeholder. Any other `{x}` (including `{}`) is
UNFILLED:template (the placeholder text is untrusted and is not echoed), checked even if no opportunity is
drafted. Substitution is single-pass: values containing braces are not re-expanded. Template and body keep
LF/CR/TAB byte-exact.

## Draft
`draft_id` = sha256(json.dumps([recipient or "", subject, body], ensure_ascii=False, separators=(",",":"))
.encode("utf-8")).hexdigest()[:16]. Subject = `Fee waiver request: <title>`. Missing/blank recipient: recipient
null, `needs_recipient` true. Invalid format (`^[^@\s]+@[^@\s]+\.[^@\s]+$` or any control char): recipient null
(the invalid string is not carried), `needs_recipient` true, `recipient_invalid` true; never raises except under
`strict`. `strict:true` raises `APPLY_REFUSED_NORECIPIENT:contact_email` for the first drafted opportunity in list
order that needs a recipient (free/unknown ones are ignored). Output:
`{drafts (input order), skipped_no_fee (sorted ids), fee_unknown (sorted ids), scope}`. Ids are kept byte-exact.

## Forbidden keys (casefold, "-" to "_", exact; whole request refused)
Precedence SEND > SPEND > SUBMIT > NOCREDS; within the winning class the alphabetically first MATCHED table key is
the suffix (`APPLY_REFUSED_SEND:approval_token`); non-matching key text is never echoed.
- SEND: send, approve, approved, approval, approval_token, smtp, token, email_send, sender, smtp_host, smtp_port, smtp_user
- SPEND: pay, waive_fee, fee_action
- SUBMIT: register, submit, attempt
- NOCREDS: login, password, username, credentials, otp, api_key, access_token, refresh_token, bearer, pass, passwd
Cross-unit parity with S4.8's table is not independently verified here; an earlier
reported SEND-list difference remains unresolved by this unit's tests.

## Refusal table (ValueError("APPLY_REFUSED_<REASON>[:token]"); tokens are only schema fields or table keys)
| Code | When |
|---|---|
| BAD_TYPE:request | request not a dict |
| SEND:<key> / SPEND:<key> / SUBMIT:<key> / NOCREDS:<key> | forbidden key at any depth |
| OVERSIZE:request | scan budget exceeded, checked before any container is read or descended into and ahead of every other refusal that the scan or later steps could raise: more than 10000 distinct dict/list/tuple objects, a dict with more than 32 keys, a list or tuple with more than 1001 items, or nesting deeper than 32 levels (request = level 0) |
| BAD_TYPE:key | non-str dict key at any depth (after the forbidden scan finds nothing) |
| UNKNOWN:request / UNKNOWN:profile / UNKNOWN:opportunities | key outside the allowlist (key text never echoed) |
| BAD_TYPE:as_of / profile / template / opportunities / strict | wrong type (as_of also for a non-ISO date; opportunities also for a non-dict element or a duplicate id) |
| EMPTY | opportunities list empty (no suffix) |
| OVERSIZE:opportunities / template / as_of / profile / id / title / contact_name / deadline | over cap, checked BEFORE clean_text. Caps: opportunities 1000, template 20000, as_of 64, profile values 200, id 128, title 200, contact_name 200, deadline 100; a filled body over 20000 = OVERSIZE:template |
| EMPTY:<id\|title> / CONTROL_CHARS:<as_of (unreachable: ISO check runs first)\|name\|school\|template\|id\|title\|contact_name\|deadline> / BAD_TYPE:<name\|school\|id\|title\|contact_name\|deadline\|contact_email> | policy.clean_text and type refusals; clean_text limits equal the caps so its own over-length code never surfaces (a test asserts this) |
| BAD_TYPE:fee | see fee grammar |
| UNFILLED:template / UNFILLED:name / UNFILLED:school / UNFILLED:deadline | unknown placeholder / used placeholder with a missing value |
| NORECIPIENT:contact_email | strict and a drafted opportunity's recipient is missing or invalid |
| UNAPPROVED | RESERVED, never raised (no approval path exists) |

## Implementation choices (not requirement quotations)
1. `EMPTY` for an empty opportunities list has no suffix (literal reading); an `EMPTY:opportunities` form is the alternative.
2. `opportunities` must be a `list` (a tuple is BAD_TYPE:opportunities); the forbidden/non-str scan still walks tuples.
3. Step 5 checks only that `as_of` is a str; the caps run next, then the ISO shape (BAD_TYPE:as_of, so "" and control characters are BAD_TYPE:as_of), then clean_text. An over-long as_of is OVERSIZE:as_of.
4. A blank (whitespace or empty) profile name/school counts as MISSING (UNFILLED only if used), not EMPTY; None is also missing.
5. Within step 8 an opportunity's field types are checked as id, title, contact_name, deadline, then contact_email (the recipient shape), then caps id, title, contact_name, deadline, then clean_text in the same order.
6. contact_name and deadline may be blank strings (blank contact_name falls back to the default; blank deadline is missing).
7. An invalid recipient string is not carried (recipient null); strict treats missing and invalid the same.
8. Top-level unknown-key suffix is `request` (no schema parent field exists above the request).
9. policy.check is not called (its six rules have no code path here); policy.clean_text and policy.scope are used.

## Additive repair on live-main floor (2026-10-11)

The delta rejects calendar year zero under ISO YYYY-MM-DD validation (caps still
precede date parsing). Recipient control checking now uses a local explicit Unicode
Cc/Zl/Zp category tuple over the raw input, not only C0/DEL over stripped text. Invalid
recipient behavior remains flags/null under nonstrict and NORECIPIENT:contact_email
under strict; there is no send or new permission path. Stdlib unicodedata is the
only new import. Full validation matrix: S4.3-validation-matrix.md.

## Recipient-address domain carve-out

Only the recipient validator pins the local category tuple (`Cc`, `Zl`, `Zp`)
instead of reading the shared helper's changing category set. Raw characters in
these categories, including leading and trailing controls, are refused before
stripping can turn them into a valid address. Zs edge padding (ordinary spaces
and NBSP) is accepted and stripped. Interior Cf characters such as U+200B remain
accepted and preserved, including in the returned draft recipient and the
`draft_id` hash input. This preserves the recipient validator's prior behavior;
it is an explicit recipient-address-only exception, not permission to accept Cf
on other echoed or hashed text surfaces. Mailbox existence is not verified.

## Request scan budget (added by the resource-order repair)
The forbidden-key scan walks the request under a fixed budget: 10000 distinct containers (an object reachable twice counts once), 32 keys per dict, 1001 items per list or tuple, depth 32. The checks run on a container before it is iterated, so an oversized or hostile structure is refused as `OVERSIZE:request` without being read. The scan accepts exact builtin `dict`, `list` and `tuple` objects only: a subclass of any of them, anywhere in the request, is refused as `BAD_TYPE:request` before it is read, because a subclass can misreport its length or iterate more than it reports. This is a disclosed behavior change: subclass inputs were accepted before. The refusal is raised when the subclass is found, ahead of any forbidden-key class. The 1001 item cap is the unit's own opportunities cap plus one, so a 1001-item opportunities list still reaches its own `OVERSIZE:opportunities` refusal; 1002 or more is refused by the scan. The other numbers are this unit's choices, sized far above any valid request (at most about 1005 containers, 6 keys per dict, depth 3). Dict keys get the same treatment, in this order, on discovery: (1) a key that is a `str` subclass is refused as `BAD_TYPE:request` untouched, so an overridden `casefold`, `replace` or length is never run; (2) an exact `str` key longer than 200 characters is refused as `OVERSIZE:request` on its raw length, before any normalization; (3) only then is the key normalized (casefold, `-` to `_`) and matched against the forbidden-key tables. The key cap is this unit's choice. Both refusals precede every forbidden-key class, like the container rules, and a bounded key keeps its existing class and precedence. A non-`str` key that is not a `str` subclass (for example an int) is unchanged: `BAD_TYPE:key` after the forbidden-key scan. Behavior for requests inside the budget is unchanged.
