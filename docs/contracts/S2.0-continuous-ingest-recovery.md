# S2.0 / row 102 supplied-file ingestion repair

This is a repair to c32.continuous_ingest, not completion of the literal Atlas
spec. No router, worker scheduler, source fetch or outbound request is added.

## Recovery format

The path supplied as state_path now has two required companions:
`state_path.sqlite3` is the authoritative local database and `state_path.lock`
is the nonblocking single-worker lock. Preserve the database when moving or
backing up state. The JSON file is a bounded diagnostic mirror, version 2,
with current-directory checkpoints, counters and a dedupe cardinality. It no
longer holds every historical hash. Deleting only the mirror does not lose
recovery. Losing the database is data loss, not a supported restart procedure.

Each batch transaction stores newly admitted hashes, record/duplicate/byte
counts and input byte offset together. Exceptions inside the transaction roll
back all three. Interruption after commit but before mirror writing recovers
from SQLite. Record counts survive interrupted runs. Run count and elapsed time
cover only completed invocations; throughput excludes interrupted elapsed time
and must not be presented as a calibrated sustained-capacity benchmark.

## File contract

Inputs are supplied local UTF-8 JSONL files. A line is at most 100000 bytes,
including the newline. Missing final newlines are unfinished input, not malformed
records: they await completion and are not checkpointed. Invalid UTF-8 and
invalid JSON complete lines count as malformed; blank lines are skipped.

Unchanged completed files are not reopened and do not consume max_files_per_run.
Touch-only mtime changes to completed files do not reopen them or recount duplicates.
Changed mtime triggers a stored-prefix comparison (whole file for files up to
8 MiB). A changed prefix re-ingests; a matching prefix skips without recount.
Same-size rewrites beyond the prefix, or with unchanged mtime, are unsupported.
Appended data reopens completed files. Inode/device replacement and truncation
restart at offset zero with historical content dedupe intact. The first 4096
bytes of the committed prefix are fingerprinted to catch some in-place rewrites
and inode reuse. This is not a whole-file integrity guarantee. Changed active
prefixes beyond that window, and same-size same-mtime changes to completed files,
are unsupported. Inputs must otherwise remain append-only. No other process may
modify database/state files. Use a trusted local directory, not a shared hostile
filesystem. Symlink input/state paths fail closed. The worker is Linux-local;
network-filesystem locking semantics and distributed workers are unverified.

## Memory and disk

Historical hashes and checkpoints are in SQLite, not a Python set or JSON array.
SQLite's page cache is configured to 2 MiB. Python holds at most one batch of
batch_size bounded lines plus at most 1000 current filenames/checkpoint mirrors.
Worst-case batch bytes are batch_size * 100000; this is a bound, not a small
memory promise. SQLite/allocator overhead is additional. Disk use increases with
historical hashes and filenames; no retention, quota or automatic cleanup is
implemented. Backpressure is a report, not enforced admission or throttling.

Version-1 JSON imports are limited to 8 MiB and validated before admission.
Larger legacy archives refuse and need a separate reviewed migration. The importer
preserves supplied legacy counts; it cannot reconstruct counts lost by earlier
crashes. Existing legacy offset interpretation is retained for normal UTF-8
newline files; historical encoding/pathology compatibility is unverified.

## Evidence required for landing

Builder regressions cover actual subprocess os._exit after committed batch,
transaction rollback, append, partial final line, replacement, truncation,
mirror deletion, worker contention, migration, oversize state/line, symlinks,
parameter caps and disk-backed dedupe. Independent auditor must reproduce these
and inspect transaction ordering. Builder tests alone are not independent audit
or production clearance.

## Oversize-file quarantine

An oversize line commits the preceding good batch and a persistent quarantine
marker together, without consuming the poison line. The worker continues to
later files and reports `{file, reason}` in `quarantined`. Unchanged quarantined
files are skipped on future runs, with no duplicate recount. Changing device,
inode, size or mtime admits another attempt from the saved checkpoint. A touch
of a still-poisoned file only rechecks the poison line, not the committed prefix.
Removing/quarantining file contents is the caller's job; no input is moved,
rewritten or deleted. Quarantine is a durable worker exclusion, not a physical
isolation guarantee. Quarantined files remain included in pending_after.

Records behind an oversize poison line remain un-ingested until the caller fixes
the file. Later files still run. Quarantine does not skip past or discard that line.


The fingerprint now streams up to 8 MiB in 64 KiB chunks. Changed mtime on a
completed file at most 8 MiB checks its entire content before skipping. Beyond
8 MiB, only the first 8 MiB is checked, so same-size tail rewrites remain out of
scope. Unchanged mtime still skips without a content check. An existing database
created with the earlier 4096-byte hash format may re-ingest a completed file
once on changed mtime to establish the longer fingerprint; content dedupe avoids
new-record duplication, but its duplicate counter increases for that migration.
