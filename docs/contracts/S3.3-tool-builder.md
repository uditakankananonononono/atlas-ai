# S3.3 tool-builder (module c34)

Supplied requirement excerpt: "monitor companies and able to autonomously build algorithms and tools for all of their needs"

Source: supplied requirement excerpt. The design below narrows the implementation to offline draft scaffolds, not autonomous monitoring or delivery.

## What the code does
`backend/app/modules/c34/tool.py` exposes `run(request) -> dict` and `scan_source(source) -> list`. Given one supplied need for a company she named, it returns `{files, draft: true, scope, ...}` where `files` holds `tool_<id>.py` and `test_tool_<id>.py` strings from fixed templates for four need types: csv_transform, scorer, deduper, report. Substitution for "autonomously build ... all of their needs": one scaffold per supplied need, never unsolicited delivery. Nothing is written to disk, fetched or run.

Input: `{"as_of":"YYYY-MM-DD","requested_by_owner":true,"company":"...","need":{"id","type","description","fields"}}`. Exact keys, no extras. `as_of` must be a real date. need id matches `^[a-z][a-z0-9_]{0,31}$` (it becomes a filename). Fields: 1 to 16 unique names matching `^[a-z_][a-z0-9_]*$`.

Emitted code is stdlib only (csv, io, unittest), and `scan_source` (ast) rejects other imports, `open`/`exec`/`eval`/`compile`/`__import__`/`getattr` and similar calls, and system/popen/urlopen/connect attributes. `run` scans its own output and refuses UNSAFE if a template ever fails the scan.

## Refusal table
| Code | When |
|---|---|
| PROTO_REFUSED_UNSOLICITED | requested_by_owner is not exactly True |
| PROTO_REFUSED_NOSPEC:type | type not one of the four templates |
| PROTO_REFUSED_SPEND | description asks to buy, pay, subscribe, invoice (via c30.policy.check) |
| PROTO_REFUSED_UNSAFE[:field] | description asks for network, scraping, messaging, posting, trading, login or accounts; or emitted code fails the ast scan |
| PROTO_REFUSED_BAD_TYPE:<field> | wrong type or shape, bad field name or id, bad as_of, duplicates, more than 16 fields |
| PROTO_REFUSED_EMPTY:<field> | blank company/id/description, no fields |
Text hygiene (control chars, length) comes from `policy.clean_text` with prefix PROTO.
Disclosed dependency: free-text hygiene (company, id, description, as_of) is delegated to the shared helper `c30.policy.clean_text`. As of main c96aeb8c that helper is repaired: it enforces strict string type (subclasses refused), rejects the full Unicode format (Cf) category, and applies the raw length cap before any strip/scan. This unit inherits the repaired behavior. Local request/need cardinality checks precede set construction. Need type is capped at 32 characters before enum membership. Field names are capped at 64 characters before regex checks, a tightening from the prior uncapped identifier grammar (retained).

Local validation repair: local container and element checks are exact built-in types, not isinstance - `type(request) is dict`, `type(need) is dict`, `type(fields) is list`, `type(ntype) is str`, and `type(f) is str` per field, so dict/list/str subclasses are refused. Key validation order at both dict levels is COUNT (len) first, then strict key type (`type(key) is str`), then the SET allowlist, so hostile keys are never hashed or compared before the type gate and allowed-name str-subclass keys are refused. The isinstance uses inside `scan_source` operate on ast nodes, not caller boundaries, and are intentionally unchanged.
Order of bounds in `run`: request and need are checked by key count before their key sets are built; the need type is length-capped (32) before the template lookup; each field name is length-capped (64) before the name pattern runs. Over-long type or field refuses BAD_TYPE:type or BAD_TYPE:fields.

## Pure-offline applicability note
Of the six standing rules (spend, outreach, fakeacct, autopost, scrape, trade) none has a code path here: the unit has no network, file-write, send, post, payment or account function. A test asserts the module exposes only `run` and `scan_source` and imports only ast, datetime, re and the policy helper. Nothing in an input field can grant any permission; extra keys are refused.

## LIMITS
Scaffolds only; does not understand the company's real needs beyond the supplied description.
It does not monitor companies, deliver anything unsolicited, or run what it generates. Templates are fixed and small; generated tests are smoke tests, not proof the tool fits the need. Description screening is keyword based and can refuse harmless text or miss rephrased requests; the ast scan, not the keywords, is what bounds the emitted code.

Repair note: the company string appears only in the `COMPANY = repr(...)` line of the emitted module, never in its docstring, so quotes or backslashes in it stay string data. If an emitted file ever fails to parse, `run` refuses `PROTO_REFUSED_UNSAFE:<file>` instead of raising SyntaxError.
