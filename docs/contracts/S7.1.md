# S7.1 / c36.ev - Opportunity EV ranker

## Source pin
Owner words (verbatim, exact substring): "Able to build up my personal brand, make me money, trade with it, invest, and predict markets etc". Only "make me money" is in scope here; trading and prediction belong to other units.
Local record: cross-account builder package; message identifiers, character counts and offsets and provenance are held privately and are intentionally not reproduced here. DESIGN text in the spec is the spec author's scope text, not the owner's words.

## What it does
`run(request) -> dict` ranks supplied opportunities by expected value from supplied numbers.
- EV = p_success.point x payoff.base - cash - hours x hourly_value, all in the request base currency. EV_low uses p.low and payoff.low, EV_high uses p.high and payoff.high.
- Rank by EV descending, then fewer hours, earlier deadline, id.
- Currency: `currency` is the base. Each payoff has its own currency; cash is in the payoff currency unless `cost.currency` is given; hourly_value is in base. Any non-base currency needs `fx = {as_of, rates_to_base}` covering it. Originals and the rate with its as_of are printed per item and in `fx_used`.
- Time: days_to_deadline = deadline - as_of. Deadline before as_of goes to `expired` and is never ranked. Equal is allowed. weeks_available = max(1, ceil(days/7)).
- Spend segregation: an opportunity with cash cost > 0, or `requires_spend: true`, is never in `ranked`. It is listed in `not_actionable_without_separate_approval` with EV shown for information and the note "spending needs the owner's separate per-action approval outside this unit". No input field moves an item into `ranked`; there is no approval input.
- Outreach: `requires_outreach` items carry the flag `draft_only_needs_approval`. Nothing is sent.
- Plan: greedy by EV per hour (zero-hour items first), positive EV only, kept feasible against a deadline-prefix hours budget (hours, never cash): for every member deadline d, the total hours of all members with deadline <= d must be <= hours_budget_per_week x weeks_available(d). A positive-EV candidate that would break any prefix is skipped, listed in `plan.greedy.over_budget` and flagged `over_budget` on its ranked row. Each plan block prints `usage`: per member deadline, used hours vs capacity hours. The exact brute-force optimum over actionable items is reported for up to 15 actionable items, with `gap_ev` = optimum - greedy. Brute-force ties prefer fewer hours, then smaller id list. Above 15 it is not computed and says so.
- Output: floats rounded to 6 places from exact Fraction arithmetic, a constant banner "Expected values from supplied estimates; not a promise of income.", `warnings`, and a `scope` block from the shared policy helper.

## What it does not do
No spending, sending, posting, trading, account creation or fetching. No market data, no taxes. Estimates are inputs, not facts.

## Policy applicability (no local adapter)
Uses the landed helper `app.modules.c30.policy` for `clean_text` and `scope`. `policy.check` is not called: it always raises, and this unit has no action path for it to guard. Of the six standing rules, spend and outreach are the only ones an input could name. They appear only as data flags, which this unit reports and never acts on. The tests prove the module exposes no function other than `run`, imports only offline stdlib modules plus the policy helper, and defines no function whose name suggests send, post, pay, spend, trade, purchase, register, submit, fetch, scrape or email.

## Refusals (`ValueError("MONEY_REFUSED_<REASON>[:field]")`)
| Reason | When |
| --- | --- |
| GUARANTEE:<field> | name, notes, label or other caller text (id, source_url) contains guarantee, risk-free, risk free, will earn, sure thing or certain profit (case-insensitive). Caller text is NOT scanned for all, every, best. |
| NOINPUT:<field> | a required field is missing or null |
| BADPROB:<field> | a probability is non-numeric, outside [0,1], or low <= point <= high fails |
| CURRENCY[:<ccy or fx field>] | a non-base currency has no usable rate: missing fx, missing as_of or rates table, rate missing, non-positive, non-finite, bool or string |
| BAD_TYPE:<field> | wrong type, non-finite or negative number, bad ISO date, bad currency code, unknown kind, duplicate id, payoff low <= base <= high fails, over 256 opportunities |
| EMPTY:<field> | blank text, or an empty opportunities list |
| CONTROL_CHARS / TEXT_TOO_LONG | raised by the shared `policy.clean_text` with the MONEY prefix |

## Generated text rule
The unit's own text uses "highest" only beside a computed number (for example "highest EV: 280.0 (o4) of 8 ranked supplied"). A test scans `summary` and `banner` for unqualified all, every and best.

## Limits
Up to 256 opportunities. Interpretation choices (IC): the "single_item_dominates" warning (an item with at least half of total positive EV and a high-minus-low spread above its EV), treating `requires_spend` as a spend, optional `notes` and `label` text fields, and the refusal reason chosen for payoff ordering (BAD_TYPE).
