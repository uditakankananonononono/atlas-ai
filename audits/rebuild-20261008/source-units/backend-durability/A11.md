# A11: durable Chroma adapter acceptance

Source: technical-spec, Database: "ChromaDB as a dedicated vector store for long-term memory and semantic search."

The prior acceptance used an EphemeralClient. This increment verifies the existing ChromaMemory adapter against a real PersistentClient in separate Python interpreters: one writer, then two fresh readers. Both tenants use the same item ID and distinct document canaries. Each fresh reader retrieves only its tenant's document; the Chroma SQLite backing file exists after the writer exits.

Command: `PYTHONPATH=backend python -m pytest tests/test_chroma_durable_acceptance.py tests/test_technical_architecture_real_backend.py`

Observed: 5 passed on Python 3.12.14. Separately, 15 existing backend/adapter/workflow architecture tests passed. Those old tests include configured Celery, a fake Redis client and provider transport fixtures; this count is not live acceptance of those integrations.

## Still open

Repository search finds ChromaMemory and RedisStreamBus only in their definitions, not product consumers. This proves adapter durability and tenant collection separation, not product LTM ingestion through Chroma, authorization of tenant identifiers, multi-client concurrency, crash recovery, or hosted operation. Existing product retrieval uses a separate SQL/vector pipeline. A11's dedicated product-store requirement remains open until that integration is designed and exercised. No production data or services were changed.
