# A10: real pgvector storage and distance-query acceptance

Source: technical-spec: "pgvector extension for dense embeddings".

A private pgserver database loads the actual vector extension and creates only MemoryEmbeddingRow's table, avoiding unrelated global SQLAlchemy metadata. It commits three 1024D embeddings, disposes and reconnects the client engine, and orders tenant-a rows by the database cosine-distance operator. Exact assertions verify near/far ordering, distances zero/one and exclusion of the tenant-b canary. A direct SQL insertion of a 2D embedding fails against the 1024D database column.

Command: `PYTHONPATH=backend python -m pytest tests/test_pgvector_live_acceptance.py`

Observed: 1 passed. pgserver's bundled pgvector extension control file specifies 0.6.2; the test also checks the installed extension version is nonempty. Server version is recorded in the review report. Engine disposed and scratch server cleaned up after testing. No hosted Supabase provisioning or production migrations.

## Boundary

This verifies actual pgvector storage, committed client reconnect, server-side cosine ordering and database dimension rejection. The tenant predicate is explicit in the query; this is not row-level security or authenticated authorization. It does not prove index use, ANN performance, database restart persistence, a model embedding provider, RetrievalPipeline product consumers, or hosted deployment. A09 remains separately open.
